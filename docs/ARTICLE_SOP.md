# 文章维护 SOP

适用于新增或更新模型架构、数据集及部署系统文章。源码放在 `docs/` 及其分类子目录；网页由 `build_site.py` 生成。贡献与 PR 流程见 [CONTRIBUTING](../CONTRIBUTING.md)。

## 1. 先明确对象与证据

写作前记录文章讨论的是哪个模型、数据集或版本，收集官方论文、项目页、仓库、模型或数据卡。核对论文版本、代码提交和查阅日期；源码链接优先固定到 commit，避免后续更新改变依据。

首页日期表示**所述方法或版本首次公开的年月**，不是本地文件修改时间。论文首发、模型发布、代码开放和版本更新可能不同，按文章对象选择 `kind`，有差别时写入 `note`。无法核实的字段先继续查证，不用猜测填满。

把证据层次写清楚：作者报告的实验结论、当前官方代码提供的能力、本地分析推断，以及实际跑过的验证各是什么。配置入口的存在不等于对应性能已经验证。

## 2. 写一篇能顺着读完的文章

标题后第一段直接概括“它解决什么问题、用什么数据或机制、产出什么、适用范围是什么”。首页卡片取第一个非标题段落并截到 200 字符，因此不要先放长版本说明或“本文将介绍”。来源与核对信息可紧随摘要。

尽量用同一个连续任务贯穿全文。例如以“拿起杯子 → 倒水 → 把杯子放回”为例：先说明相机记录了什么，再说明任务如何切分、标注怎样对应视频、模型读入什么、预测什么，最后解释如何评估完成情况。示例必须标明是讲解用途，不能写成数据集实际包含的任务或已经完成的机器人实验。

按对象选择以下内容，不为凑齐章节发明不存在的模块：

| 内容 | 应回答的问题 |
|---|---|
| 数据与输入 | 来源、规模、许可、采样/划分；图像、语言、状态等输入如何对齐，哪些值依赖配置？ |
| 标签与输出 | 人类动作、手部位姿、语言或机器人控制标签分别是什么？单位、坐标系、有效性 mask 和输出语义是什么？ |
| 模型或处理管线 | 每个模块接收与输出什么，关键表征如何连接？数据集文章可用采集→处理→标注→使用的管线替代模型结构。 |
| 训练与推理 | 哪些模块冻结/更新、用什么目标；推理时可获得什么条件，哪些信息只存在于训练？ |
| 实验与限制 | 数据划分、任务、本体、指标、对照和硬件是什么？报告的是 ID/OOD、离线、仿真还是实机结果？ |
| 来源与后续阅读 | 在相应事实旁附直接支持它的一手链接，文末汇总重要入口和关键代码文件。 |

Egocentric 数据尤其要说明：人类第一视角视频不自动等于机器人动作监督；手部轨迹也不自动等于可执行的关节或末端指令。若涉及转换或迁移，写清转换假设及已有验证。

Mermaid 图沿用站点风格，用有含义的节点名和清晰箭头表示数据流；代码图的标识符对应真实源码。复杂结构拆图，避免一张图过宽。公式使用 `$...$` / `$$...$$`，表格写清单位；构建后检查图、公式、表格及深浅主题。

## 3. 放置源文件并登记页面

### 路径与链接

可使用分类子目录，例如：

```text
docs/egocentric/25.HumanEgo_Architecture.md
```

`SECTIONS` 的 `file`、`PAGE_TOPICS` 和 `PAGE_DATES` 的键都使用**相对于 `docs/` 的完整路径**：`egocentric/25.HumanEgo_Architecture.md`。

输出目录保持扁平：上述源文件生成 `docs/site/25.HumanEgo_Architecture.html`，不生成 `site/egocentric/`。所有文章 basename 必须唯一；序号用于稳定命名，导航顺序由 `SECTIONS` 的声明顺序决定。文章中的站内网页链接使用输出名，例如 `./24.OpenWAM_Architecture.html`，不要按源目录层级拼网页地址。维护文档仍使用普通 Markdown 文件链接。

### 三处必需登记

在 `docs/build_site.py` 中：

1. **`SECTIONS`：** 将文章放入合适侧栏类别。新类别需有 `title`、`desc`、`pages`；文章项例如 `{"file": "egocentric/25.HumanEgo_Architecture.md", "label": "HumanEgo"}`。`children` 用于同一类别中的父子页面。
2. **`PAGE_TOPICS`：** 用同一完整路径登记现有领域 ID 的集合，从 `KNOWLEDGE_DOMAINS` 选择；例如涉及视觉表征和示范学习时可选 `{"perception", "imitation"}`，应按文章实际内容填写。
3. **`PAGE_DATES`：** 用同一完整路径登记 `month`（`YYYY-MM`）、`kind`、官方来源 `source`，必要时增加 `note`。填写前核实首发时间，不使用文件 mtime 或此次入库日期。

**类别与标签不同：** `Egocentric` 类别是导航中的主题分组；`perception`、`imitation` 等标签表示跨文章的知识领域，一篇文章可以有多个。创建目录或类别不会自动生成领域标签。只有现有领域确实无法表达新内容时，才扩展 `KNOWLEDGE_DOMAINS`。

如果新文章适合作为首页知识导图的代表入口，同时更新 `KNOWLEDGE_PATH_STAGES` 的节点名称、说明和扁平输出链接。普通新增文章通过注册进入卡片与领域计数，不必为每篇文章增加导图节点。

## 4. 本地检查

首次按 [README 快速开始](../README.md#快速开始)安装依赖，之后在仓库根目录执行：

```bash
source .venv/bin/activate
./deploy.sh --build
python -m unittest discover -s tests
git diff --check
```

打开 `docs/site/index.html`，确认新类别、卡片、日期来源、领域筛选和知识导图链接；进入文章检查目录锚点、相邻文章链接、表格、公式和全部 Mermaid 图。再看窄屏与深浅主题，确认正文和图表可读。

构建错误先检查完整路径是否一致、源文件是否存在、basename 是否重复，以及日期/标签是否遗漏。`CONTRIBUTING.md` 和本 SOP 属于维护文档，不登记为站点文章。不要通过修改 `docs/site/` 修问题，应修改源文档或生成器后重新构建。

## 5. 推送、合并与发布

检查本次差异后提交源码、推送功能分支并创建 PR，在 PR 中写清内容变化、来源和验证结果。合并到 `main` 后，在干净且已更新的 `main` 上重新检查并执行：

```bash
git switch main
git pull --ff-only origin main
source .venv/bin/activate
./deploy.sh --build
python -m unittest discover -s tests
./deploy.sh --verify
```

当前项目采用 Cloudflare Pages Direct Upload，**推送 GitHub 不会自动上线**。`./deploy.sh --verify` 会构建、发布到生产站点，再逐页比较线上与本地内容；它不是只读检查。发布脚本固定使用生产分支 `main`，从功能分支执行也会更新正式网站，因此发布应使用已合并的版本。

若发布成功但校验出现差异，保留具体页面与错误信息，核对线上响应及当前发布版本；不要把“已上传”当成“全部页面已验证”。本地检查不需要发布凭据，发布环境按 README 的 Cloudflare 登录方式准备。
